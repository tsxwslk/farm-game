# 架构：时钟与存档

**状态**：v0.1 框架
**范围**：技术选型、激活计时实现、午夜日结、存档结构、数据校验、场景与交互
**不包含**：具体模块划分与接口定义（待原型验证后补充）

---

## 1. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 构建 | Vite + TypeScript | 与既有工程习惯一致，冷启动快 |
| 状态 | Pinia（或等价集中 store） | 整棵状态树可序列化，存档天然是 JSON |
| 持久化 | IndexedDB（idb） | 容量足够，支持结构化克隆 |
| 渲染 | TypeScript + Canvas 2D 场景，DOM/CSS 界面 | 已选二维像素光影田畦；模拟、输入与寻路独立推进，场景按脚点排序，界面保持文字可读性 |
| 部署 | 静态托管 | 无后端，无运维 |

**明确不做**：Three.js/WebGL 三维场景、自由旋转相机、额外游戏引擎、Service Worker 复杂缓存。Canvas 绘制与模拟时钟分离，作物生长、产出和日结由模拟推进。首版沿用静态托管，跨设备续玩先走存档文件。[跨设备续玩](#44-跨设备续玩)

## 2. 时钟模型

### 2.1 活动分钟与日结状态

`activeGameMinutes` 是累计活动分钟，`dayIndex` 是已确认开始的日号（从 0 起）。`phase` 取 `playing` 或 `dayReview`。每个活动日 1,080 分钟，日内偏移为 `activeGameMinutes − dayIndex × 1080`。活动时从 06:00 加上偏移，日结时偏移恰为 1,080，仍显示刚结束的日号。季节与年均从已确认的日号派生。

### 2.2 统一推进入口

页面可见、有焦点、未手动暂停且处于活动日时，才接受帧增量。正常流速下 1 秒折算 1 游戏分钟；帧间隔最多取 250 ms。失焦、切标签、手动暂停、恢复与读档时重置帧基准，系统时间戳仅供展示。

```
remaining = (dayIndex + 1) * 1080 - activeGameMinutes
step = min(requestedMinutes, remaining)
advanceWorld(step)          // 按温度变化、动作完成等边界分段
activeGameMinutes += step
if step == remaining:
    enterDayReview(dayIndex)
```

倍率和手动步进共用此入口。到午夜先提交旧日最后一段实际进度，处理恰在午夜达成的动作，再冻结并生成日结。超出的步进量舍弃。以第 1 天 23:59 为例，无论请求 1 分钟还是 1 小时，最多推进 1 分钟。

### 2.3 确认进入次日

日结汇总当日收获、加工、上锚和已经入账的收支，从满足条件的提示与剧情中选出本夜文案并保存。翻页只改阅读位置。等待期间冻结作物、加工队列、暴露、冷却、玩家动作及其动画；手动存档始终可用。

确认操作携带结算日号，只接受与当前 `dayReview` 相符的请求。一次提交中日号加一、归档已展示的剧情、建立新日日志、切换季年并刷新日事件，恢复 `playing`。此刻活动分钟数不变，日内偏移归零。重置帧基准，并按当前焦点与暂停状态恢复推进。

## 3. 换日与恢复

刷新顺序固定：天气 → 商店 → 委托 → 月相 → 动物 → 土壤 → 余绪显形。当日新增产出记入新日；首次活动采样按新日环境先判定冻死、休眠或停长，再给存活暴露株结算当日霜品质。温度变化和当日新栽也走相同判断。[时钟季节与天气](../策划/时钟季节与天气.md)

进入日结和确认次日各保存一次。日刷新标记、日号、阶段及剧情标记一起写入同一 IndexedDB 事务，写入成功后才接受下一次确认。写入失败保留可重试的原状态。快照写入串行，避免较早的自动保存覆盖确认结果。读档直接还原保存的阶段；活动页和日结页均不补算离线时长。

## 4. 存档结构

### 4.1 顶层

```ts
{
  schemaVersion: number,
  savedAt: string,          // 仅用于展示，不参与逻辑
  activeGameMinutes: number,
  dayIndex: number,         // 最近一次已开始并完成日刷新的日号
  phase: "playing" | "dayReview",
  dayLog: {...},            // 当日事件与已入账收支
  review: null | {...},     // 结算日号、摘要、文案 ID、页码
  storyFlags: {...},
  world: {
    weather: {...},
    soil: {...},
    plots: [...],
    species: {...},         // 已种植实例
    inventory: [...],       // 含批次来源与数量
    jobs: [...],            // 在制品、实际投入批次与剩余活动分钟
    scene: {...},           // 地图、角色位置、进行中的互动与动作进度
    ledger: {...},          // 发现、已获品质、首次收录、途径与稿酬记录
    economy: {...},
    buildings: [...],
    unlocks: {...}
  },
  settings: {...}
}
```

发现与收录分别按条目 ID 保存。未点亮源条目首次取得合格原料时设定截止活动分钟与轮次 ID，原料批次随之记录轮次。加工开工时锁定实际扣料批次，生成中间品时继承实际投入来源及轮次；从仓库取回或加工旧批次沿用原始轮次。只有重新取得源原料才能在旧轮次到期后新开一轮。

使用线完成时，按事件发生的累计活动分钟查验实际消耗批次的轮次和截止时刻。一次推进跨过多个事件时按事件发生时刻顺序判定，恰好在截止分钟完成视为超时。剩余时间由截止活动分钟减去当前累计活动分钟计算，跨日和读档均沿用存档里的原值。产出或交付、通过查验后的首次点亮和应付稿酬在同一状态变更内提交。日结读取日记账，不再发奖。

### 4.2 版本迁移

**从第一天就必须有迁移机制**，否则第三次改数据结构就废档。

```
migrations: Record<number, (save: any) => any>
```

加载流程：读存档 → 逐版本链式迁移 → 校验 → 载入。如导入只有累计分钟的旧结构，沿用旧日历解释为活动日（恰在边界表示新日已开始），补上日号与空日记。旧档已点亮与已付记录保留，不追缴或补发；未亮源条目从新取得的合格源原料起算。旧库存缺少轮次时沿用普通用途，无法追溯的半成品沿用已有来源信息。

从 v5 迁入 v6 时，背包和仓库里每一份旧粗盐换算成三份调味用量，保留原批次时限和能腌制的份数。已开工的配方沿用原完工时刻和投入批次。盐灶里的在制粗盐与待领粗盐按新配方产出十二份。

从 v6 迁入 v7 时，已有植株补记为樱桃萝卜，空地的作物标识为空，并初始化委托记录。柳湾地块索引保持原序。南山道与柳湾共用同一模拟状态，出入口切换位置，存档直接记录落点。

从 v7 迁入 v8 时，保留原有的 16 格背包和 24 格仓库。扩容在格子数组末尾添加空格，容量随格子数组保存。加载时校验容量档位及当前快捷栏排号。

从 v8 迁入 v9 时，初始化芥菜余绪的采集状态和小白菜种子的当日库存。柳湾试玩天气按存档的日号读取一张固定预报表，无需另存随机状态。旧档若正处于雨天活动日，仍未浇水的种子从读档时开始生长。午夜读档保留当天状态，确认次日后再按天气浇水。

### 4.3 存档策略

| 时机 | 方式 |
| --- | --- |
| 手动保存 | 立即写快照 |
| 自动保存 | 每 3 分钟一次 |
| 页面隐藏前 | 写一次 |
| 关键节点 | 进入日结、确认次日、解锁完成、建筑落成 |

**外加**：一键导出 JSON 到本地文件，防清缓存丢档。导入时走同一套迁移链路。

### 4.4 跨设备续玩

**首版用 IndexedDB 自动存档，加 JSON 导出和导入。** IndexedDB 保存在当前浏览器的本地站点数据里。换设备前，用游戏内「存档」菜单导出一份已保存的快照，将文件放进 iCloud Drive、OneDrive 或常用网盘，再在另一台设备从游戏内导入。文件同步交给网盘，读写哪一份存档由玩家确认。现有 Demo 使用的 localStorage 同样是本地数据。[试玩版说明](../../prototype/pixel-farm/README.md)

1. **导出。** 暂停当前推进，将最新状态写入 IndexedDB，等待事务完成，再下载带版本号的 JSON。建议文件名包含存档名、游戏日和导出时间。文件存进度、批次、进行中的加工、钱袋、物志与结算状态。屏幕方向和输入偏好可留在各自设备。
2. **导入。** 用文件选择器读取 JSON，检查格式和 `schemaVersion`，按迁移链补齐旧字段，再校验完整存档。确认前展示存档名、游戏内日期和时刻、导出时间。遇到损坏文件或超出当前游戏支持版本的文件时保留原档。默认导入为独立档位，选择替换时先备份原档，替换和备份在同一事务里提交。
3. **续玩。** 以快照里的活动时间和阶段恢复。日结档打开后停在原日结页，在制品保持剩余时间。另一台设备上的旧副本仍可打开，所以换回来时也要导出当前设备的新进度，再确认读入。真实时间戳用来识别文件，档位冲突由玩家选。

**自动云同步可作为后续功能。** 如果需要手机打开就读到电脑的最新进度，游戏仍先保存到 IndexedDB，再用同一份快照格式上传到有身份验证的云端存储。首版文件互导可以独立交付。云同步用稳定的存档 ID 和服务器版本号。写入时提交上次读取的版本号，版本冲突时保留本地与云端两个快照，让玩家按游戏时间和保存信息选择。重复上传复用同一次提交标识，掉线时先保住本地存档，恢复联网后再尝试同步。

验收用两个独立浏览器环境。设备 A 在活动日开工后导出，设备 B 导入并接着玩，再在午夜日结导回 A。两边检查角色位置、库存、加工剩时、稿酬和日结页。另验损坏文件、新版本文件和已有档位的替换备份。

## 5. 数据驱动与校验

所有物种、天气、建筑、区域均为**纯数据表**。校验每份留种粒数为 ≥2 的整数、物种四季参数和温度边界完整、每个源条目的时限为正且至少有一条可达使用线；用跨区自然可得季并集核算季节专属生物占比 ≥50%。

**加载时必须校验**（schema 校验，如 zod 或手写校验器）：

- 开发环境：校验失败直接抛错，不静默容错
- 生产环境：跳过坏条目并记录，保证不白屏

**理由**：这个游戏的核心优势是"自己随便加内容"。如果手改数据能炸档，优势就变成了风险。

## 6. 渲染分层

| 层 | 内容 | 技术 |
| --- | --- | --- |
| 场景层 | 农场网格、地形、田畦土壁 | Canvas 2D，原生 32 像素地表拼接与缓存 |
| 实体层 | 角色、作物、建筑、动物、投影 | 透明 PNG，根部/脚点排序，接触阴影与右下像素投影 |
| UI 层 | 顶栏、背包、物志、建筑菜单 | 普通 DOM |
| 覆盖层 | 弹窗、tooltip、拖拽预览 | 绝对定位 + CSS 过渡 |

**当前场景标准。** 河畔青绿配色，固定俯视微倾视角，沿用光影田畦模式与 4 源像素土壁。正式版每个 32×32 可耕草地格种一株，樱桃萝卜保留 48×72 田间源图并按单格比例绘制。视觉高度与通行、种植坐标分开，前景作物遮挡人物时适度透显。二维镜头可平移、跟随和缩放。详见[已选实现标准](../美术/轻量立体感试作.md)。

**交付与加载。** 每个物品用稳定的资源键引用图片。田间像素素材保存为透明 PNG，程序地面保留生成器及色板，内容清单维护资源键到文件、源像素尺寸与锚点的映射。图片按资源键缓存，地面按连接与湿度缓存，保持原生像素和清晰缩放。旧 SVG 原型已清理，其 100×100 画布和 `<symbol>` 复用方案不作为当前场景素材交付要求。

旧 SVG 原型示例清单（保留供历史查阅，路径示意）：

```json
{"pea":{"seedling":"图像/豌豆幼苗.svg","vegetative":"图像/豌豆成株.svg","mature":"图像/豌豆成熟.svg","item":"图像/豌豆.svg"}}
```

物品表和存档引用稳定标识，文件名可调整。首屏只请求当前农田和可见背包图，翻开物志再请求该页缩略图；同一资源键合并请求。数量、品质、选中框由界面叠加。同物异色可选一个默认图合堆展示。收获物保持透明底，田间帧沿用固定根部锚点；存活多年生有待采果实时优先显示成熟图，采后再选生长或休眠图。

交付时检查清单中的文件、画布、必需阶段和引用是否完整。可选出土帧缺失时从幼苗开始；正式画面遇到坏文件时显示名称与占位图，保留条目和库存。每次发布更新变更资源的版本 URL，带走对应缓存。[美术交付规范](../美术/作物与物品美术规范.md)

### 6.1 场景、建筑与操作

固定俯视地图保存地块坐标、地形、通行标志与交互点。Canvas 2D 绘制缓存地面和像素地物，按角色脚点和建筑基部的纵坐标排序；树冠、屋檐可单独盖在角色前面。WASD 与点击寻路共用通行网格：点击生成格子路径，接近障碍旁的交互点后才开始动作。TypeScript 在获准推进时更新状态，渲染读取位置与动作进度，不以动画帧数结算玩法。下表的钓鱼、挖矿状态约定沿用，早期 SVG 动作示意在当前场景中使用对应像素帧和程序线段呈现。

| 场景 | 玩家操作与画面 | 游戏状态何时改变 |
| --- | --- | --- |
| 建造 | 选建筑后，鼠标下显示占地预览；无效格标红，门口标出可达入口 | 确认时复验地形、占地、入口、建材和预算，一次扣料扣款、登记建筑并更新通行网格。点入口打开生产面板 |
| 钓鱼 | 岸边选可达钓点，角色切换抛竿姿势。浮标 SVG 随等待、咬钩、收线切换动作，咬钩时接受收竿输入 | 状态依次为抛竿、等候、咬钩、收线及完成或脱钩。判定使用活动进度和输入窗口；成功仅入包一次并记发现。钓点条件取当前区域、时段与天气 |
| 挖矿 | 走到矿点相邻格，点击挥镐。角色臂和镐绕握点转动，矿点按剩余耐久切换裂纹图 | 每次挥击到命中时校验距离、工具和目标，扣一次耐久；矿点耗尽结算一次掉落，再显示已采状态 |

场景动作保存目标 ID、阶段、剩余进度、已判定的结果和背包待领取产出。读档可继续等候或挥击；进入日结冻结在当前阶段，确认后的首次推进再校验目标是否仍有效。目标失效则结束动作，已经结算的命中或掉落按记录保留。容量不足时缓存已确定的产出，领入背包时登记发现。CSS 动画只呈现这些状态，暂停时停止插值；命中、咬钩与完工由模拟判定，不依赖动画结束事件。

### 6.2 区域、区块与玩法点位

区域定义地形、季节与天气环境、入口和出口。区块保存范围、地形与装饰资源、通行格以及相邻区块的连接。玩法点位以稳定 ID 引用地块、建筑或岸边交互格，挂接已有的种植、养殖、加工、采集、钓鱼和挖矿规则。添加一段河岸时，由内容表配置可达交互点及当地鱼类条件。地图应校验入口与出口相通、必要交互点可到达。

镜头移动时挂载视野所及的区块，跨边界时可同时显示两侧。区块移出视野后可卸载绘制节点，地块、加工队列与互动结果仍保存在世界状态中。远处设施在获准推进的活动时间内继续加工，作物按实际经过的温度、天气和季节区间累计生长。午夜日结对所有区域一起生效。首版区块尺寸、预加载范围和资源预算由正式场景实测确定。

### 6.3 原型与当前场景

早期柳湾水彩原型验证过地形拼接、双布局、寻路、种植与采集，记录保留在验收文档；该 demo 及素材已从当前工作区清理，可从 Git 历史恢复。

正式版从仓库根目录运行 `npm run dev`。柳湾使用 48×30 地格和 IndexedDB 存档，支持 JSON 导入导出。地图串起田记所、起步菜畦、林缘、旧制盐台、河岸与南侧扩垦地。南山道入口目前有独立地图视野、小径、路碑和返程点。

[柳湾可玩 Demo](../../prototype/pixel-farm/index.html)保留 34×20 地图、64×64 种植单元、山道出口标记和版本化 localStorage 存档，供对照早期开局与视觉。地形、干湿与道路连接由 `ground-verify.cjs` 校验。

### 测试操作

[时钟与钱币测试台](../../prototype/时钟与钱币测试台.html) 可直接操作 1×、5×、20×、暂停、前进 1 小时、前进至次日 06:00，以及增加 100 / 1,000 文。本页使用独立的会话数据。此原型演示的是早期直接跨日。正式测试面板的「到午夜」须停在日结，再单独确认次日；测试面板应调用与生产相同的时间推进与钱包记账函数；当来源为测试加款时，仅改变余额，跳过稿酬、首次收录和任务收入判定。

## 7. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
